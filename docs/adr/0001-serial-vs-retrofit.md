# ADR 0001 — Serial-port control vs LinuxCNC retrofit

**Status:** accepted 2026-09-04 (supersedes the project's founding assumption; revised against
[`docs/_machine-facts.md`](../_machine-facts.md))

## Context

The makerspace has an EMCO PC Turn 50 training lathe whose original DOS control PC is gone. The
project began from a community-sourced premise: the control box's DB9 is RS-232, the box speaks
plain G-code with CTS handshaking, and therefore either a small "sender" program — or, as often
suggested, "just LinuxCNC" — could drive the machine through that port.

The machine's own manuals and schematics, photographed and consolidated in
[`docs/_machine-facts.md`](../_machine-facts.md), overturned that premise:

- The DB9 (bulkhead `X300`) is a 3-wire **RS-485** multidrop bus (pin 2 GND, pin 3 DATA−,
  pin 8 DATA+). Connecting RS-232 hardware to it is electrically wrong and risks damage.
- The DOS PC drove it through a proprietary **memory-mapped ISA card** (`Y4A013000`, 4 KB
  dual-port RAM at CC000–CFFFF). **It is not a UART.** There is no text byte-stream protocol,
  no documentation of the framing, and the original card and software left with the dead PC.
- The interpreter and planner ran **on the PC**; the cabinet (CPU board `Y4A012000`, PLC
  "SPS 2000", stepper power card `Y4A018000`) is an executor speaking an unknown proprietary
  bus protocol.

Meanwhile the same documentation made the retrofit path *more* concrete: the CPU board's `X104`
ribbon header carrying differential step/direction for both axes now has a documented pinout
(see [`docs/60-retrofit-design.md`](../60-retrofit-design.md)).

### Why "LinuxCNC drives the machine over the serial port" is not possible

This misconception is why the project exists, so it gets spelled out once, here.

LinuxCNC is not a G-code *transfer* program. It is a **motion controller**: its real-time core
closes a control loop at a fixed servo period (typically 1 kHz), computing joint positions every
millisecond and emitting **step pulses** (or servo commands) through hardware it controls
directly — a parallel port, a Mesa FPGA card. It needs a low-latency electrical path to motor
drives. It has no concept of handing a program to another CNC control and waiting; that job
belongs to a DNC sender, which LinuxCNC is not.

And even if a sender were the goal, this machine's port could not receive it: the port is an
RS-485 device bus whose framing was generated by ISA-card hardware, carrying an undocumented
low-level protocol between the PC-resident interpreter and the cabinet's executor boards — not
G-code, not on a UART. Both halves of "LinuxCNC over the serial port" fail independently.

What LinuxCNC *can* do is (a) run as a **training simulator** today, and (b) *become* the
machine's motion controller in a retrofit, where it emits step pulses into the existing stepper
power stage — which is exactly the retrofit design.

## Options considered

1. **Drive the machine over the DB9 (non-invasive).** Requires reverse-engineering a
   proprietary RS-485 protocol with no reference implementation, no transmitting master to
   observe, and possibly non-UART framing. Discovery ladder and honest odds:
   [`docs/30-serial-protocol.md`](../30-serial-protocol.md) — assessed as *may not be tractable
   at all* unless the original software (and ideally the ISA card) is found.
2. **Retrofit: replace the CPU board with a Mesa 7i96S + LinuxCNC** (open the box, keep the
   5-phase motors, drive the existing power stage via `X104`). Documented down to a connector
   pinout; reversible; costs money and breaches the box. Design:
   [`docs/60-retrofit-design.md`](../60-retrofit-design.md).
3. **Full gut** (new motors, drives, VFD). Most expensive, least reversible; rejected as a
   first move in doc 60 §3, retained as fallback if the power stage or spindle drive is dead.
4. **Do nothing invasive; LinuxCNC as simulator only; keep discovery alive.** The machine keeps
   its original (currently unusable-without-PC) control; volunteers train on the simulator;
   the tools in [`tools/`](../../tools/README.md) pursue archaeology and capture at zero risk.

## Decision

**Option 4, with option 2 held ready as the documented escape hatch.**

The owner's standing decision is to stay **non-invasive**: the control box is not opened, the
machine keeps its original control, and LinuxCNC runs as a training simulator
(`linuxcnc/sim/emco-pcturn50/`). The retrofit is a *future option*, engineered on paper
(doc 60 + the skeleton config in
[`linuxcnc/retrofit/emco-pcturn50-7i96s/`](../../linuxcnc/retrofit/emco-pcturn50-7i96s/)) so it
can be executed deliberately rather than improvised — but **nobody buys parts or opens the box
until the revisit conditions below are met.**

Stated honestly: the evidence has moved **toward** the retrofit. The serial route went from
"find the baud rate" to "reverse-engineer a memory-mapped ISA card's bus with no reference
implementation", while the retrofit went from "community folklore about an ISA header" to a
documented, differential-pair-level interface. The decision to wait is a decision about
invasiveness and stewardship of a working artefact, not a bet that the serial route will win.

## Consequences

- The sender project (`sender/`) remains fully useful — against the simulator and
  `tools/virtual-emco.py` today, and as the operator UI for whichever control path eventually
  wins. Its `PlainGcode` dialect is a labelled development fiction, never a claim about the wire.
- Discovery work continues at zero risk per the ladder in doc 30 §4 (archaeology → memory-window
  emulation → passive RS-485 capture → guarded probing), with every session logged.
- No tool in this repo may present itself as able to move the real lathe over the DB9, and
  every wire-facing tool carries the RS-485-only electrical warning.
- The retrofit design and skeleton config are maintained as living documents so the option
  stays executable, including the bench-testable parts (Mesa card config, HAL structure) that
  need no machine access.

## Revisit when

Any one of these re-opens the decision, through an update to this ADR:

1. **Discovery is exhausted**: a defined search budget (suggested: one season of forum/archive
   hunting alongside other work) produces neither the original software nor the ISA card, and
   passive capture finds a silent bus.
2. **Discovery succeeds but the result is impractical**: the protocol turns out to be a
   real-time master-driven bus a PC application cannot safely speak.
3. **The original electronics die**: the CPU board, PLC or their power path fails — the
   non-invasive path then preserves nothing, and doc 60 §1 applies immediately.
4. **The owner's priorities change**: e.g. the machine is wanted as a working trainer sooner
   than discovery can deliver.

Until then: the box stays shut.
