# 31 — The RS-485 message layer, from WinNC's own log

**Status: analysis of a public artefact, 2026-11-14. Nothing here was seen on
this machine's bus.** It's a companion to [doc 30](30-serial-protocol.md),
which owns the discovery ladder and the findings log; §6 below is a findings-log
entry drafted for doc 30 §8, and §4 lists the corrections doc 30 needs.

## 1. The artefact

[`485tr-1.txt`](https://www.forum.linuxcnc.org/media/kunena/attachments/25860/485tr-1.txt),
posted in the LinuxCNC forum thread
["EMCO PC Mill 50 RS485 data capture"](https://www.forum.linuxcnc.org/38-general-linuxcnc-questions/37204-emco-pc-mill-50-rs485-data-capture)
(2019), is the output of WinNC's built-in recorder, "Aufzeichnung der RS485
Schnittstelle", from a **PC Mill 50** (AC88 generation). It isn't a wire
capture: WinNC logs the messages it hands to and takes from the ISA card, so
it shows the message layer and nothing below it. No sync bytes, no checksums,
no bit rate, no idle traffic.

How close that is to this lathe:

- **Same card:** the PC Mill 50 uses the same `Y4A013000` ISA card (a
  groups.io question about fitting a PC 55's card in "the Y4A013000" slot of a
  PC 50 mill). Second-hand, but consistent with the card's jumper page.
- **Different machine and probably a newer software generation:** a mill (axes
  X, Y, Z and a fourth, "XYZI" in the init message) under WinNC, where this
  lathe ran DOS `FANOT` v2.0 (1993). Message codes may differ; the framing
  (addresses, length rule) is more likely to carry over than the code table.

`tools/winnc-485-log.py` reads the format; its tests are
`tools/test_winnc_485_log.py` (run with `WINNC_485_LOG=…/485tr-1.txt` to
also check the numbers in this document against the whole file).

## 2. The record format

    O ------ 485 Out       Nr.:     2   Zeit:    0.000 ------
       L=  6   Z=  0   Q=250   Code= 50=2
        0D 61                                                   .a
    I ------ 485 In        Nr.:     1   Zeit:    0.055 ------
       L=  7   Z=250   Q=  0   FCode= 527 .. AC-Eingaenge
        C8 00                                                   ..

| Field | Meaning | What the whole file shows |
|---|---|---|
| `O`/`I` | direction, from the PC | 255 out, 523 in, over 446.8 s |
| `Nr.` | sequence number per direction | +1 every message in both directions, no gaps: nothing was dropped from the log |
| `Zeit` | seconds since the recording began | coarse: 401 distinct values for 778 messages, the first 10 at 0.000 |
| `L` | message length | **payload + 4 for every outbound message, payload + 5 for every inbound one** |
| `Z` | destination (Ziel) | outbound to 0 or 16 only; inbound always to 250 |
| `Q` | source (Quelle) | outbound always from 250; inbound from 0 or 16 |
| `Code` | outbound: one character | 33 distinct, digits and letters (`1`, `S`, `N`, `c`, `p` …) |
| `FCode` | inbound: a number with WinNC's name | 23 distinct in 500–567; WinNC names 18 of them |

The addresses: **250 = PC, 0 = axis controller (AC), 16 = PLC (SPS)**. The
names come from WinNC's own FCode labels ("AC-…", "SPS-…"). Every message
goes between the PC and one node; the nodes never address each other, so the
PC is the only master, as doc 30 §1.1 assumed.

The constant L overheads say the frame carries a fixed header beyond what the
log shows, one byte longer inbound. A guess that fits: destination, source,
code and a length or checksum byte outbound (4), with the inbound FCode
needing one more byte than a character code does (FCodes run past 255, so two
bytes). That's an inference; the wire capture (doc 30 rung 2) settles it.

Multi-byte values are little-endian (`D0 07` = 2000, `20 4E` = 20000).

### What the sequence suggests (interpretation, may be wrong)

- **Start-up** (t = 0–0.2 s): a burst of configuration to the AC (`1`
  with 54 bytes ending in the axis letters "XYZI", then `2` `3` `6` `S`
  `A` `E` `T` `K` `L` `J` `Q` `V` `W` `X` `Z`), answered by
  `527 AC-Eingaenge` (inputs), `503 AC-Reset-Quit`, `519 SW-Version`
  (`0D 02 17 02`) and a stream of `504 AC-BuferInc`. Then the PLC
  (`B` with 83 bytes, `D` `C` `R` `U`), answered by
  `508 SPS-Quit-Loop`, `522 SPS-OB-Signale`, `510`, `523 SPS-Tool`,
  `509 SPS-M-Code`, `526 SPS-Meldungen`, `511 SPS-Reset-Quit`.
- **Flow control:** `504 AC-BuferInc` always carries `01` (96 times).
  It reads as the AC returning one buffer credit, so the PC keeps a
  window of outstanding blocks rather than waiting for each.
- **Block markers:** every outbound `p` is answered by a `515 AC-BlockM.
  Per` with the same byte (`05`, `0B`, `0C`, four times over), and
  `514 AC-BlockMarker` counts 0–10 (skipping 5) four times: the AC
  reporting which program block it is executing, four runs of a ~12-block
  program. That matches the forum's "demo program of about 8 blocks".
- **M-codes go to the PLC:** `S` to address 16 carries `4D 03 00`,
  `4D 05 00`, `4D 1E 00` ("M" 3, 5, 30), and `509 SPS-M-Code` comes back
  with `01 03 00`, `01 05 00`, `01 1E 00`: an acknowledged M3/M5/M30.
- **`S` to the AC** carries `61 00` + a little-endian word (`D0 07` =
  2000, `20 4E` = 20000): a parameter by number, plausibly feed or speed
  in some unit. Unknown.
- **`505 AC-S-Command`** is the most frequent message (236), six bytes,
  a zero int32 then a small word (156–273): plausibly a status or
  position report while running. Unknown.

What the responder in `tools/dosbox-capture` would need first: the
start-up replies in the order above, one `504` per outbound block, and
`515` echoing `p`.

## 4. Corrections to the repo's documents

Two corrections, from the research of 2026-11-14:

1. **The ISA card's window is 2 KB, not 4 KB.** Manual p.45 (IMG_0791,
   `docs/img/b-interface-card-jumpers.jpg`) lists eight 2 KB windows,
   CC000–CC7FF (the default), CC800–CCFFF, … CF800–CFFFF; the card is
   assigned CC000–D0000. The owner's notes and the `_photos-0614`
   transcription already said 2 KB. Fixed in this commit:
   `_machine-facts.md`, `tools/README.md`, `tools/dosbox-capture/README.md`.
   **Still to fix in doc 30** (left alone because it has uncommitted edits
   elsewhere): the §1.1 diagram ("default CC000–CCFFF"), §2.1 K4 ("4 KB
   dual-port window CC000–CFFFF") and the 2026-09-04 findings entry ("dual-port
   RAM window CC000–CFFFF", which is right as a range but should say 2 KB
   default CC000–CC7FF).
2. **"PCCOM" is the AC95 card, not `Y4A013000`.** EMCO's own DNC-interface
   document lists the device types "PCCOM-Karte (AC95), RS485-Einschubkarte
   (AC88)" ([EMCO PDF](https://www.emco-world.com/fileadmin/pim/Beschreibung_der_DNC-Schnittstelle__Bin_Modus__01.pdf)).
   This lathe's schematic calls its card "PC-Einschub RS 485". Binder A is a
   WinNC manual "valid from Version 13" that covers AC95 machines, so its
   PCCOM pages (IMG_0629, IMG_0630, IMG_0676) may describe the other card.
   Fixed in `_machine-facts.md` and `tools/dosbox-capture/README.md`;
   doc 30 doesn't name PCCOM.

Doc 30's "not a UART" (K4, §1) is right about the PC side and should say so:
the software only sees shared RAM, but on the wire the link is probably
asynchronous framing (§5).

## 5. Below the message layer: the best estimate

From the same research (sources in its report; confidence noted):

- **Probably asynchronous UART framing, not SDLC/HDLC.** A first-hand report
  logged the traffic "without trouble" with a cheap USB-RS485 adapter in
  parallel; a later first-hand report says the card, the axis controller and
  the optional keyboard each have an Intel **80C196**, whose serial port has
  no HDLC and no clockless synchronous mode.
- **Possibly 9-bit address-mark framing** (the 80C196's mode 2/3, where a
  node only wakes on bytes with the ninth bit set). That fits the
  destination byte the log shows. At 8N1 a 9-bit frame reads as framing
  errors, which would also explain reports that logic-analyser decodes "made
  no sense" (second-hand).
- **Bit rate: unknown,** and possibly not a standard one (the 80C196 divides
  its crystal; 187.5k or 375k are candidates).
- **Idle heartbeat:** "a pattern of 00's every 58–59 seconds when idle", not
  in WinNC's log (first-hand). If the AC sends it unprompted, a passive
  capture on X300 with the machine powered and no PC could catch it, and it
  would give the bit rate and framing without a master.
- The KD240 capture records parity and framing errors per byte
  (`kd240/src/parmrk.rs`), so a 9-bit frame shows up there as a
  parity-error pattern on every address byte, once the rate is right.
